# LZ4 GPU/Hybrid 变体测试价值指引

更新时间：2026-04-15

## 1. 目的

本文件用于总结：

- **什么样的内核/主机优化值得优先测**；
- **什么样的尝试测试价值低，应列入黑名单或低优先级**；
- 避免继续做“无头苍蝇式”的平铺乱试。

## 2. 高测试价值候选（优先）

### 2.1 单阶段、单机制、信号隔离清楚

优先测这类候选：

- 只动一个阶段；
- 只改一个准入规则/计数规则/复制规则；
- 能清楚解释“为什么这版应该比上一版更轻/更稳”。

### 2.2 与 CPU 原始实现存在明确差异、且 GPU 实现理由可解释

高价值条件：

- CPU 有一套成熟分支/阶段策略，GPU 当前实现已经做了偏离；
- 或 GPU 当前实现新增了某种启发式/开关，但其收益尚未被证实；
- 可以明确回答“为什么 CPU 不这么做，而 GPU 值得这么做/不值得这么做”。

### 2.3 已有正向信号的保守深挖

典型例子：

- `count_batch32_first` 已经跑出小而干净的正向，就值得继续做**更保守或更可解释**的深挖；
- `search_step_warmup_shift5_cap4` 这类吞吐极强但 ratio 代价大的版本，只适合作为旁线参考，而不是主线深挖起点。

### 2.4 能直接帮助删功能/减复杂度的主机端扫描

高价值主机端候选：

- host/device 通信路径、map/unmap、event/wait、steady-state 同步点这类有明确分段时间的过程；
- hash table buffer 生命周期、alloc/reuse、device-only / host-visible 这类能直接影响 `buffer_alloc/upload/download` 的特殊轴。

补充：`pipeline / overlap / compaction` 这条 host 扫描线已经完成并退休，后续不再算“高价值待扫项”。

## 3. 低测试价值候选（低优先级/黑名单）

### 3.1 同时改多个决策门、难以归因

低价值特征：

- 一个候选同时改 search、lazy、count、emit；
- 结果不管好坏都说不清是谁导致的；
- 需要大量手工审核才能理解发生了什么。

### 3.2 已证明会系统性伤害主判据的“重手”版本

当前 LZ4 GPU 已知低价值方向：

- **重型 overlap-cost / 全局 cost-score**：已证明能把 ratio 和解压拉正，但会把压缩主判据打穿；
- **全局坏桶惩罚 / 全局 non-overlap 偏置**：已证明压缩端系统性塌陷；
- **literal copy 额外快路径复制**：已证明明显负向；
- **没有严格边界证明的 pre-match lazy**：出现过 standalone mapping failure。

这些方向若要重启，必须先给出“为何这次比旧失败版更轻、更安全”的明确论证。

### 3.3 只是在噪声内抖动、没有超噪声证据的重复尝试

低价值特征：

- 上一版已经完全落在 control 噪声内；
- 新版本只是做同类微调，没有新的机制解释；
- 预计结果仍只会落在噪声里。

### 3.4 主机端继续保留“明显无效”的可开关功能

凡是经过扫描后确认：

- 没有稳定收益；
- 只增加状态空间和维护复杂度；
- 还会污染对比矩阵；

应优先进入删除/冻结名单，而不是继续留在默认配置周围反复测试。

当前 `lz4_gpu` 已明确进入此名单的是一批历史低价值 host 开关分支。

## 4. 当前经验提炼

### 4.1 当前高价值主线

- `count_batch32_first` 一类：**小步、ratio 中立、主判据有超噪声正向**；
- 主机侧与调度侧：**能用分段时间清楚解释收益归因**的变体；
- hybrid：**分配/调度模型** 与 **host-side communication**。

### 4.2 当前低价值主线

- 过重的 overlap-aware chain gate；
- 没有严格安全边界证明的 aggressive lazy；
- 已证明只会把压缩率或吞吐单向打坏的重复重试；
- 已退休 host 功能（`pipeline / overlap / compaction`）的无新机制重启。

## 5. 使用要求

每次设计新候选时，必须先在记录里回答：

1. 它属于哪个阶段？
2. 为什么它比历史失败版更轻/更稳？
3. 预计主收益落在哪个指标？
4. 失败时最可能坏在哪个指标？

答不出这四个问题的候选，默认不进入正式验证。
